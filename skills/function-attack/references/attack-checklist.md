# 攻击清单细则（8 步）

> 本文件是 `SKILL.md` 的展开版：每步做什么、产出什么、判据是什么、常见错误是什么。
> 目标不是「跑完所有工具」，而是**每一步都能回答「做了没有、判据过没过」**；不通过就产出反例。

## 1. 先定风险级别（决定投入）

| 级别 | 判定 | 默认时间盒 | 变异抽样 | fuzz |
|---|---|---|---|---|
| 低 | 纯函数、输入受控、无外部 IO、已有示例测试 | 30 min | 10–15 | 不适用 |
| 中 | 解析/编解码、有错误分支、被多处调用 | 45–60 min | 15–30 | 仅解析/协议入口 |
| 高 | 安全/金额/权限/数据迁移、输入来自外部、历史出过事故 | 60–120 min | 30–50 或全量（夜间） | 60–300 秒起，必要时更长 |

风险级别由用户给；用户没给时按上表判断，并在报告里写「假设风险级别」。

## 2. 步骤 0：读契约与调用点

**动作**

1. 读 docstring、类型注解、错误约定、单元测试里已有的期望；
2. `grep` 所有调用点：输入从哪来、输出到哪去、返回值被谁消费；
3. 找出副作用：写文件/网络/日志/全局状态/随机/时钟；
4. 写出契约摘要五要素。

**产出**：五行契约摘要 + 调用点清单（文件:行号）。

**判据**：能回答「哪些输入是合法的、非法输入应发生什么、成功时返回什么、有没有副作用、能否重复调用」。
**常见错误**：只看函数体不读调用点，把调用方保证的前提误判成函数 bug；契约缺失时不标「假设」直接开测。

## 3. 步骤 1：输入域与边界

**动作**

1. 按 `references/boundary-matrix.md` 的维度表，逐维列出：合法范围、边界值、非法值、契约期望；
2. 每个高风险维度至少一条正常 + 一条负向用例；
3. 用示例测试或 `pytest.mark.parametrize` 固化边界表；工具可用时可用属性测试生成。

**产出**：维度表（维度 / 边界 / 期望 / 用例 / 结果）。

**判据**：每个高风险维度有测试，或书面写「不适用 + 理由」（例如「越界由类型系统保证」）。
**常见错误**：只测空串不测空白；只测负数不测 0/-0；忽略类型边界（`None`、布尔当整数）；忽略长度/精度/Unicode。

## 4. 步骤 2：错误契约

**动作**

1. 逐条构造非法输入，核对五件事：异常类型、消息关键字段、副作用、资源清理、重试语义；
2. 对照同模块其他函数的失败方式是否一致（值域哨兵 vs 异常 vs 返回空值不能混用）；
3. 检查「不该抛异常」的合法输入是否真的不抛。

**判据**：非法输入按契约失败；无脏数据、无泄漏；失败方式模块内一致。
**常见错误**：只断言「抛了异常」不看类型；异常消息不带出错值导致无法排查；失败路径留下半写文件。

## 5. 步骤 3：属性测试

**动作**

1. 从 `references/property-patterns.md` 的六类属性里挑 3–5 条：至少 invariant + round-trip（若可逆）+ oracle 或 metamorphic 之一；
2. 写生成器（Hypothesis 或手写 + 参数化），失败时收缩/删减出最小反例；
3. 每条属性写一句「它为什么可能被违反」，避免空转。

**判据**：属性全部通过，或失败给出最小反例并解释；属性不是把实现抄一遍。
**常见错误**：同义反复（用实现推算期望）；生成器域太窄（永远只生成合法输入）；属性恒真（例如只断言「不抛异常」）。

## 6. 步骤 4：变异抽样

**动作**

1. 有工具（mutmut 等）→ 限定到目标函数所在文件/行，抽样 10–30 个；
2. 无工具 → 按 `references/mutation-playbook.md` 手工注入 5–10 个变异体，逐个跑现有测试；
3. 统计 killed / survived / timeout / unviable；给 survived 处置。

**判据**：分数 ≥70%（关键函数 ≥80%），或每个 survived 有书面处置。
**常见错误**：把「测试全绿」当变异结果；survived 只写「补测」不写补哪条断言；不记录抽样范围导致不可复现。

## 7. 步骤 5：fuzz（按需）

**动作**

1. 只在解析/解码/协议/安全边界上做；纯业务函数跳过并写理由；
2. 有 Atheris → 按 `references/fuzz-harness.md` 写 harness，先跑 corpus 再 fuzz 60–300 秒；
3. 无 Atheris → 用 `scripts/probe_inputs.py` 跑边界 smoke，或手写随机生成器 + 固定种子；明确写「不是覆盖率引导」。

**判据**：无崩溃/超时/未捕获异常；有则稳定复现并最小化。
**常见错误**：把随机输入测试叫 fuzz；崩溃不能稳定复现就下结论；对纯计算函数硬上 fuzz。

## 8. 步骤 6：差分 / 蜕变（按需）

**动作**

1. 有第二实现（旧版本/参考库/跨语言实现）→ 差分：同输入比输出/错误码；
2. 无 oracle 但能定义输入变换 → 蜕变：验证变换前后关系；
3. 每个不一致 triage：谁错了、还是规格未定义。

**判据**：无不一致，或每个不一致有结论。
**常见错误**：把「两个实现不同」直接判为新实现错；浮点比较不用容差；MR 写反。

## 9. 步骤 7：固化与稳定性

**动作**

1. 每个最小反例固化成一条示例测试（输入 + 期望 + 复现命令）；
2. 重复跑 3–5 次、随机顺序跑，查 flaky；
3. 确认旧测试不受影响。

**判据**：新测试稳定通过；无 flaky；旧测试全绿。
**常见错误**：只修不固化，问题回归；新测试依赖执行顺序或真实时间。

## 10. 停止规则

- 低风险 + 步骤 1–3 全绿 → 可停在步骤 3，报告写「未做 4–6 及理由」。
- 函数是薄封装/纯转发、变异分数低 → 先判断「是否值得测」，可标 skip + 理由。
- fuzz 连续多日无新覆盖 → 停止加时间，换 target 或换手段。
- 时间预算用完 → 停，报告写清「做到哪一步、还剩什么」。
- 任何时候都**不允许**用「测试全绿」当结论。

## 11. 证据规则

- 每个 ❌ 必须给：输入、期望、实际、复现命令；能附文件:行号就附。
- 每个 ✅ 也要给证据（跑了哪条命令、多少用例、耗时），不能只写「通过」。
- 工具输出只引用关键行，不要贴整屏日志；保留命令以便复现。
- 区分「观察到」和「推断」：没验证的写「待确认」。

## 12. 报告模板

见 `templates/attack-report.md`；最小结构是：目标 / 契约 / 调用点 / 8 步结论与证据 / 最小反例四件套 / 变异统计与存活处置 / 未覆盖风险。
