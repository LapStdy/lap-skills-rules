# 性能取证（perf-evidence）

把「感觉慢 / 想优化」变成可复核的证据链：基线、复杂度、热点、最小改动、正确性证据、前后对比、回归门禁。没有数据不宣布提速；没有正确性证据不改热点。

## 前置条件

| 依赖 | 要求 | 缺了怎么办 |
|---|---|---|
| Python 3.11+ | `scripts/bench_stats.py`、`scripts/diff_harness.py` 要能跑 | 缺 Python 就手工统计，产物标「工具未用」 |
| 可运行的被测代码 | 能在目标机器上重复执行，输入可固定 | 不能在目标机跑就写明「非目标机数据」并降置信 |
| 可回退的基线 | git 仓库 + 可复现的基线提交 | 没有版本控制先用快照复制，否则无法回退 |
| 稳定机器 | 关掉其他负载；能固定 CPU 频率更好 | 噪声大就增加重复次数，报 median 与 IQR 而不是单次数值 |
| 可选工具 | `pytest-benchmark`、`py-spy`、`asv` | 缺失时用 `timeit` + `cProfile` 降级，写明少了什么证据 |

## 何时用、何时不用

| 用户意图 | 走哪里 |
|---|---|
| 这个函数慢/卡、怎么优化、提速、复杂度多少、O(n)、profile/火焰图、benchmark、性能基线、防止性能回归 | **本技能** |
| 已有 bug（报错/堆栈/「线上偶发超时」要根因定位并修） | `diagnosing-bugs`（本技能只做性能证据，不做根因定位） |
| 从零写实现、先写哪个失败测试、红绿循环 | `tdd` |
| 整个 PR/分支的规范轴 + 需求轴评审 | `code-review` |
| 测试本身脆/过度打桩/覆盖假象（静态体检） | `brooks-test` |
| 架构级性能：缓存策略、并发模型、模块切分 | `codebase-design`（本技能只做函数级取证，联合时各出各的产物） |
| 批量安全小改动自动修 | `brooks-sweep` |
| 单个函数怎么写规范、契约、docstring | `function-spec` |
| 该不该做这次优化、目标与顺序、有没有更优解 | `first-principles`（本技能只对已决定优化的对象取证） |

判据：问「慢多少、贵在哪、改完更快没」→ 本技能；问「为什么坏了/怎么修」→ `diagnosing-bugs`；问「结构/模块怎么切」→ `codebase-design`。命中相邻技能时，一句话写明路由理由与技能 id，随即停止；**输出只含「路由技能 id + 一句理由 + 相邻技能的下一步」**，不展开本技能步骤或产物，也不列举本技能会做什么/不做什么（否定句同样算越界，例如「不做基线/benchmark」也不要写）。

## 输入与缺省

| 项 | 缺省 |
|---|---|
| 目标 | 函数路径 + 行号（或入口命令）；没有就问一次 |
| 复现 | 一条可重复的命令 + 输入规模；不能复现先补复现，不硬测 |
| 目标类型 | 提速 X% / 只防回归 / 只回答复杂度；不明确时默认「先给证据，不承诺提速」 |
| 现有测试 | 先跑一遍记录绿/红；没有测试时先补最小正确性测试，或明确标注风险 |
| 环境 | Python 版本、OS/CPU、依赖版本；不同机器数据不能直接比 |
| 时间盒 | 默认 30–60 分钟；按 基线/复杂度/热点/改动/验证 分配 |
| 改代码 | 只做最小改动；不改公共签名、不改语义；用户要改语义必须先确认 |

## 第 0 步：工具与环境检测（必做，先于测量）

探测（报错即缺失）：`python -c "import cProfile"`、`python -c "import time; time.perf_counter"`、`python -m pytest --help` 里搜 benchmark、`py-spy --version`、`asv --version`、`python -c "import tracemalloc"`。

| 情况 | 做法 |
|---|---|
| 内建 cProfile / perf_counter / tracemalloc | 永远可用；开发期热点定位与计时底座 |
| pytest-benchmark 可用 | 用 `templates/bench.py` 写基准，`--benchmark-save/compare` 做前后对比 |
| pytest-benchmark 不可用 | **降级**：`scripts/bench_stats.py` 或手写 `perf_counter` 采样（≥10 次，median/IQR）；写明噪声更大、不能直接进 CI 门禁 |
| py-spy 可用 | 长驻/线上/不能改代码时采样：`py-spy top` / `record` / `dump` |
| py-spy 不可用 | **降级**：cProfile（开发期）+ 手工计时；写明缺少采样、火焰图与低开销线上观测 |
| asv 不可用 | **未做**历史趋势；用 JSON 基线 + `bench_stats.py compare` 做本机前后对比 |

记录环境：`python --version`、OS/架构、CPU、相关依赖版本。降级规则：**缺工具不拒绝取证**；必须明写「降级 / 未做」、缺了什么、结论少了什么证据；**不假装跑过工具**。

## 7 步流程（每步有判据与时间盒）

| # | 步骤 | 通过判据 | 时间盒 |
|---|---|---|---|
| 1 | 复现 + 锁定范围 | 一条命令可复现；记录输入规模 n 与调用方式；明确「只优化热点、不改语义」 | 5–10 min |
| 2 | 基线 | ≥5 次（建议 10–30），丢弃 warmup，同环境同命令；输出 median/IQR/样本数/环境 | 5–15 min |
| 3 | 复杂度 | 规模曲线至少 4 个点（n 翻倍），用时间比/斜率下结论；标出隐藏平方 | 10–20 min |
| 4 | 热点 | cProfile 的 cumtime/tottime/ncalls，或 py-spy 火焰图；定位到函数 + 行号 | 10–30 min |
| 5 | 假设 + 最小改动 | 1–3 个假设，一次只改一个、单独测量；diff 只碰热点；公共签名不变 | 15–40 min |
| 6 | 正确性四件套 | 签名不变 + 改前测试绿 + 新旧差分一致 + 契约/属性测试重跑 | 10–20 min |
| 7 | 前后对比 + 门禁 | 同环境同输入对比含离散度；达标或明确「放弃」；基线/门禁建议落盘 | 10–20 min |

每步报告 ✅/❌/不适用；不适用要写理由，不能空白。

## 复杂度判断口径

- 规模点至少 4 个（如 100/200/400/800），每个点多次采样取 median；n 翻倍看时间比：≈1 → O(1)/常数主导，≈2 → 线性，≈4 → 平方。
- 用 log-log 斜率 `k = log(t2/t1) / log(n2/n1)` 辅助结论，并给拟合质量/分段；`O(n log n)` 在常见规模下接近线性，不要过度解读。
- 结论必须来自测量；读代码只能提出假设，由规模曲线确认。
- 内存同理：`tracemalloc` peak 随 n 的曲线；优化前先确认是 CPU 还是内存瓶颈。
- 细则与陷阱见 `references/complexity-and-gates.md`。

## 正确性四件套（缺一不可）

1. **公共签名与返回类型不变**（参数、默认值、返回、异常契约）。
2. **改动前现有测试全绿**；原本就红要先记录，不能拿「测试绿」掩盖。
3. **新旧差分**：同一批输入逐条比较返回值与异常；用 `scripts/diff_harness.py`，差异必须解释并确认。
4. **契约/属性测试重跑**：至少边界 + 不变量；有 `function-spec` 契约摘要或 `function-attack` 属性测试时全部重跑。

允许的行为差异（排序稳定性、异常消息、浮点末位等）必须显式记录并取得确认；否则一律视为改坏。**不允许「优化后再补测试」**。

## benchmark 与回归门禁口径

- 基线 = 同环境、同命令、同输入的多次采样；报告 median/IQR/样本数/环境，单次计时不算证据。
- 回归判定：**median 回归 > 阈值（默认 10%）且超出基线 IQR** 才算回归；只满足一条不判失败。
- 绝对耗时阈值不进 CI（机器差异）；基线按机器/架构分文件，CI 共享 runner 只出趋势或放宽阈值。
- 基线入库要留痕：日期、原因、前后 median、环境；更新基线是显式动作，不在优化 PR 里顺手改。
- pytest-benchmark 用 `--benchmark-save/compare`；不可用时 `scripts/bench_stats.py`（JSON 基线 + compare）。细则见 `references/benchmark-baseline.md`。

## 输出模板（完整报告；缺项不算完成）

```text
目标：<path::func>（目标：提速 X% / 只防回归；时间盒 N min）
环境：<python> / <os-arch-cpu> / <依赖版本>
复现：<一条命令 + 输入规模>
基线：n=..., median=... ms, IQR=... ms, rel-IQR=...%
复杂度：n=.../.../... → 斜率 k≈... → O(...)
热点：<cProfile 或 py-spy 证据；函数 + 行号 + cumtime/tottime/ncalls>
假设与改动：
  1) <假设> → <最小 diff> → <测量结果>
  2) ...
前后对比：median ... → ...（Δ...%），IQR ...
正确性证据：签名不变 / 测试 N passed / 差分 M 条一致 / 属性测试重跑
门禁建议：<阈值 + 基线文件路径；或说明 CI 只出趋势>
未做与风险：<工具缺失、未覆盖路径、样本局限、内存/维护性风险>
结论：达标（...%）/ 无可证收益，放弃（附数据）
```

报告只含以上内容；不要打分、不要做架构/需求评审、不要顺手改无关代码。

## 停止规则

- 达到目标，或 1–3 个假设都无收益 → 停，写「放弃」+ 数据；不继续凑优化。
- 差异落在噪声内（两轮变化在 IQR 里）→ 加样本/换更稳定指标；仍不可分就判「无证据」。
- 优化需要改公共契约或语义 → 停，先确认；不擅自改。
- 时间盒到 → 交当前证据与下一步，不硬凑。
- 热点在冷路径、只执行一次、占比极小 → 写清「不值得优化」。
- 收益小于可读性/维护性/内存代价 → 写建议不做。

## 反合理化（遇到这些说法直接驳回）

| 借口 | 驳回 |
|---|---|
| 看起来是 O(n²)，直接改 | 先测规模曲线；读代码只能提假设，数据才能下结论 |
| 加缓存肯定快 | 测命中率、内存与失效成本；没有数据显示收益就不算 |
| 只跑一次，快了 3 倍 | 单次不算；≥5 次 + IQR + 同环境，报 median |
| 测试全绿，行为没变 | 测试覆盖不到全部分支；补新旧差分 + 契约/属性测试 |
| 先优化，测试后补 | 正确性保护前置；改前必须绿，改后必须差分一致 |
| benchmark 波动大，挑最好一次 | 报 median/IQR/样本数，不挑最好；噪声大就加样本或换指标 |
| 机器不同也能直接比 | 基线分机器；跨机器只比同机相对变化与趋势 |
| 没装 pytest-benchmark，做不了 | 降级 `perf_counter`/`bench_stats.py`，写明噪声更大、不能直接进 CI 门禁 |
| 这是热点，必须优化 | 热点 ≠ 值得优化；看占比、调用频次与风险收益 |

## 完成自检

- [ ] 基线含 median/IQR/样本数/环境，命令可复现
- [ ] 复杂度结论有规模曲线，不是只凭读代码
- [ ] 热点有 profiler 证据并定位到函数 + 行号
- [ ] 最小改动只针对热点，公共签名/契约不变
- [ ] 正确性四件套齐全（或有明确未做原因与风险）
- [ ] 前后对比同环境，回归口径（阈值 + IQR）写清
- [ ] 无收益时明确写「放弃」+ 数据，不编造提升
- [ ] 缺工具时写明「降级/未做」及少了什么证据
- [ ] 未越界到 `diagnosing-bugs` / `code-review` / `codebase-design` / `brooks-sweep`

## 边界

- 通用 bug 根因定位 → `diagnosing-bugs`；PR 级评审 → `code-review`；架构级性能/并发/缓存设计 → `codebase-design`。
- 不做安全小改动自动修（`brooks-sweep`）、不做测试质量体检（`brooks-test`）、不做单函数规范审计（`function-spec`）。
- 不承诺无法复现的提速；不把「感觉快」写成结论；不为了数字好看改基准输入。
