# 第一性原理寻优（first-principles）

把「要不要做、怎么做、先做哪个」从方案描述拉回到目标与可复核事实，生成并比较候选解，产出一页可拍板的「决策备忘」。本技能不评价方案写得好不好，只回答三件事：真实目标是什么；现状里哪些是必要条件、哪些是给未来预付的成本；在同样的硬约束下，有没有更省、更可逆、更快拿到验证的做法。

默认只读：不改代码、不改文档、不跑基准。用户要落文档时按 `templates/decision-memo.md` 写。

## 何时用、何时不用

| 用户意图 | 走哪里 |
|---|---|
| 「按第一性原理评估」「有没有更优解」「最优解」「方案评估」「方向对不对」「该不该做」「值不值得」「路径/顺序/形态该换吗」 | **本技能** |
| 只有一个模糊想法、还没有方案，要长出 2–3 条候选路线 | **本技能（入口 B）** |
| 方案已定，要把每个分支追问到细节闭合（字段、边界、异常、验收） | `grilling`（本技能只决定选哪条路，不负责把细节问全） |
| 模块接口、深模块、切分位置已定，要设计签名与隐藏实现 | `codebase-design`（本技能只回答「该不该有这个模块、它归内核还是插件」） |
| 代码或架构体检、循环依赖、健康分、技术债、测试质量、批量安全小修 | `brooks-*`（本技能不打分、不全量扫描、不自动修） |
| 已知 bug、报错、堆栈、偶发失败要根因 | `diagnosing-bugs` |
| 需要一次性原型来回答某个未知行为 | `prototype`（本技能只指定「验证什么、判据是什么」，原型是执行手段） |
| 性能取证：快慢、基线、热点、benchmark 回归 | `perf-evidence`（本技能只回答「值不值得优化」） |
| 单个函数的命名/契约/docstring/复杂度 | `function-spec` |
| 函数级未知缺陷、属性测试、变异测试 | `function-attack` |
| PR 或分支的双轴评审（规范轴 + 需求轴） | `code-review` |
| 从零写实现、红绿循环 | `tdd` |
| 查外部一手资料、把结论写成带出处的笔记 | `research`（本技能给候选与需核实的问题，调研由它执行） |
| 术语不一致、领域模型要重建 | `domain-modeling` |

判据：问「该不该做 / 哪条路更好 / 先做哪个」→ 本技能；问「选定之后具体怎么做 / 为什么坏了 / 慢多少 / 接口怎么切」→ 相邻技能。
命中相邻技能时，一句话说明路由理由并给出技能 id，随即停止；不展开本技能步骤与产物。

## 输入与缺省

先判定入口：

| 入口 | 用户原话形态 | 第 1 步起点 | 默认产出 |
|---|---|---|---|
| A 方案已定 | 「按第一性原理评估这个方案」「有没有更优解」「方向对不对」 | 把方案自述还原成使用场景，再写目标函数与必要条件 | 保留/调整/推翻 + 候选路线对比 + 一个决策点 |
| B 只有模糊想法 | 「我想做 X，值不值得」「该不该做」 | 从口述痛点直接写目标函数与必要条件 | 2–3 条候选路线 + 推荐 + 最小验证 |

判据：贴得出方案文档、模块表或路线图 → A；只有一段口述或一个痛点 → B。入口只改第 1 步的起点，第 2–7 步相同。

输入项与缺省：

| 项 | 缺省 |
|---|---|
| 入口 A：方案材料 | 文档、模块表、路线图、接口清单任一份；贴不出材料时按入口 B 处理 |
| 入口 B：口述痛点 | 一段话即可；缺「谁、何时、要多快得到什么结果」时问一次 |
| 目标陈述 | 用户口述的目标常是方案伪装的目标；按「什么场景下、谁、在多长时间内、要得到什么可观测结果」还原 |
| 硬约束 | 机器与网络条件、预算与人周、已有依赖、合规与账号；缺了按「不新增付费与外部依赖」假设并在表里标注 |
| 事实来源 | 本机能查到的日志、配置、源码、命令输出优先；外部资料默认只到索引级 |
| 输出长度 | 默认一页「决策备忘」≤120 行：结论 ≤5 行、三栏表 ≤10 行、候选表 ≤6 行、决策点 ≤3 行；用户明确要长报告才展开 |
| 时间盒 | 默认 60–90 分钟：目标/事实/假设 30–40 min，最小集/候选/评分 20–30 min，验证与输出 10–20 min |
| 是否改文件 | 否；只读材料。用户要落文档时按 `templates/decision-memo.md` 写 |

缺输入时先从材料和本机事实里找；仍缺的，一次只问一个必填项，不列一串问题。

## 第 0 步：材料与证据入口检测（必做，先于结论）

列出四类入口并记录可用性：

| 入口 | 怎么确认 | 不可用时怎么办 |
|---|---|---|
| 运行痕迹 | 日志目录、运行日志、事件数据；给出路径与时间范围 | 缺运行痕迹：「稳定/失败率」类判断只能给推断级，标低置信 |
| 配置与状态 | 配置文件、注册表或系统设置、数据库、环境变量 | 缺配置证据：「环境就绪」类前提一律进假设栏 |
| 源码与依赖 | 仓库路径、`git log`、依赖清单、官方 SDK 或绑定目录 | 缺源码：能力判断降到一手文档级 |
| 外部资料 | 本机能否出网；不能出网时只到索引级 | 不能出网：外部方案只进候选，写明「需 N 小时实测」，不进结论 |

完成判据：列出 ≥3 个可复核入口（路径或命令），写明出网状态与由此确定的证据等级上限。

可选：多路并行取证。入口 A 且材料多时，可开 2–4 个只读子智能体分头取证（范围与产品、架构与可靠性、工程量与治理、外部方案），每路只交事实、问题与出处；汇总时按三栏与证据等级交叉复核，子智能体的结论不直接进推荐。仅在用户允许或任务足够大时启用，并写明并行带来的 token 成本与重复取证风险。

## 主流程（7 步，每步有完成判据与时间盒）

| # | 步骤 | 做什么 | 完成判据 | 时间盒 |
|---|---|---|---|---|
| 1 | 还原真实目标 | 从使用场景写目标函数；把「必要的」与「顺带想要的」分开 | 一句目标函数 + 3–6 条必要条件；每条对应一个可观测结果，且能判「不满足」 | 10–15 min |
| 2 | 事实基座 | 填事实/假设/推断三栏，每条带证据等级与定位 | 事实栏每条有 `file:line`、日志时间戳或命令输出；假设栏每条写明「不成立时哪一块塌」；推断栏每条有推理链与失效条件 | 10–15 min |
| 3 | 拆假设 | 把方案里的隐含假设逐条与事实栏对照，判成立/存疑/推翻 | 每条假设有判定与依据；被推翻的假设必须指向受影响的模块、阶段或成本项 | 5–10 min |
| 4 | 最小充分系统 | 由必要条件推「覆盖全部条件的最少组件集」；跑换脚本测试 | 最小集逐条映射到必要条件；入口 A 下每个现有模块过换脚本测试，给出「内核/插件/可删」三选一 | 10–15 min |
| 5 | 候选解 | 按六透镜各提至少一条候选，并写清删什么 | 候选 ≥3 条、覆盖 ≥4 类透镜；每条写「改什么、删什么、代价、可逆性」；入口 A 下至少一条与现状方案正交 | 10–15 min |
| 6 | 评分选优 | 先过硬约束闸，再按四维打分，标翻转条件 | 每个候选有硬约束通过/淘汰 + 四维分数 + 翻转条件；排名第一者明确 | 10–15 min |
| 7 | 最小验证与决策点 | 为第一名设计最便宜的一次验证；按模板收口，给 2–3 个互斥选项 | 验证有预登记判据与时间盒；决策点 ≤3 个选项、一句推荐；本轮若新事实推翻已有判断，附「修正记录」 | 10–20 min |

流程规则：

- 候选生成必须晚于最小充分系统；先看现状方案再想候选，会被锚定成微调。
- 第 1–4 步未完成不得给推荐；未过硬约束闸的候选不得进推荐。
- 「修正记录」是硬性产物：新事实推翻此前判断时，写清哪条判断、依据什么、修正后结论；不静默改写（静默改写会污染后续文档与记忆）。

### 三栏：事实 / 假设 / 推断（第 2 步细则）

| 栏 | 定义 | 必须写 | 不允许 |
|---|---|---|---|
| 事实 | 本机可复核的观测 | 证据等级 + 定位（`file:line`、日志时间戳、命令与输出摘要） | 「文档里写了」不算事实（被评估的文档本身就是待核对象） |
| 假设 | 方案默认成立、但未验证的前提 | 「若不成立，哪一块塌」+ 当前判定 | 没有失效后果的假设（那只是描述） |
| 推断 | 由事实与假设推出的结论 | 推理链 + 失效条件 + 置信度 | 把推断写成事实；把一次运行当规律 |

证据等级：

| 等级 | 定义 | 示例 | 能支撑什么 |
|---|---|---|---|
| A 实测 | 本机可复现的观测 | 日志统计、命令输出、系统设置读值 | 可直接推翻假设 |
| B 原文 | 源码、配置、依赖里的定义 | `file:line`、manifest、SDK 函数签名与回调 | 可推翻「黑盒/只能界面操作」类假设 |
| C 一手文档 | 官方文档、规范、发布说明（带 URL 与版本） | 官方 API 文档、协议说明 | 支撑能力判断，不支撑本机行为 |
| D 推断 | 由 A–C 推出 | 用时序列估完成率、按启动耗时估超时概率 | 需写推理链与失效条件 |
| 索引级 | 只知道「有这个东西」，未核对 | 外部项目名、二手文章标题 | 只能生成候选，不进结论 |

口径：结论里每一行至少有一条 A 或 B 支撑；只有 C/D 的结论标「低置信」；只有索引级的写「需 N 小时实测」。证据不足不拒绝评估，降置信度并给最小验证。

### 候选解六透镜（第 5 步细则）

| 透镜 | 问法 | 典型产出 | 样例锚点 |
|---|---|---|---|
| 换集成方式 | 有没有官方库/绑定/API，把「黑盒 + 界面或日志抓取」变成函数调用 | 删掉整层适配、对账、视觉栈 | 用脚本自带的 Python 绑定替代界面自动化 |
| 换顺序 | 最硬的验收能不能提前到第 1 周；现成能力能不能先跑一段 | 第 8 天拿到真实故障分布，替代想象 | 用脚本自带定时 + 通知先裸跑 7 天 |
| 换形态 | 同样能力有没有更轻的载体 | 响应式页 + 组网替代原生 App | Web 页 + 虚拟组网替代 APK |
| 换证据 | 主证据能不能换成更便宜且更真的信号 | 结构化回调、完成集、资源余量替代截图 | 完成集 + 资源数值替代画面判定 |
| 用现成方案 | 已有产品、框架、协议覆盖多少 | 先花 1 小时实测候选，再决定是否自研 | 同类开源项目、框架自带远程协议 |
| 缩小范围 | 哪些需求是给「第二个实例、第二台机器」预付的税 | 通用性推迟到第二个真实实例出现 | 多机、多脚本移出首期路线 |

规则：

- 每条候选必须写「删掉什么」；只加不减的候选不算更优解。
- 候选必须有一条来自「换集成方式」或「换顺序」——这两类杠杆通常最大；确实不适用时写出证据。
- 「用现成方案」受证据等级约束：未核对只能进候选，不能进推荐。

### 评分选优（第 6 步细则）

硬约束闸（先淘汰，不打分）：违反任一即淘汰，并写明违反哪条——目标函数覆盖不到首要必要条件；超出预算或人周；依赖不可用的平台或网络；合规与账号不允许；不可逆地锁死数据模型或公共契约。

四维评分（1–3 分，默认等权；首要必要条件有硬验收时目标函数权重 ×2 并写明）：

| 维度 | 3 分 | 2 分 | 1 分 |
|---|---|---|---|
| 目标函数 | 直接覆盖首要必要条件 | 覆盖次要条件或间接覆盖 | 只对未来场景有意义 |
| 代价 | 净减模块、人周、依赖 | 持平 | 净增 |
| 可逆性 | 只动插件或入口，可回退 | 改动集中、回退要迁移 | 锁死数据模型或公共契约 |
| 置信度 | 关键判断有 A/B 证据 | 有 C 级文档 | 只有 D 或索引级 |

排名规则：总分高者优先；同分取可逆性高者；总分差 ≤1 视为不可分，交第 7 步验证决定，不硬排名。
翻转条件：每条候选写「若出现什么新事实，它会掉到第几位或被淘汰」；写不出翻转条件的候选说明证据没到位。

## 输出模板（缺项不算完成）

按 `templates/decision-memo.md` 输出一页「决策备忘」，十一节（0–10）齐全、总长 ≤120 行：

| 节 | 内容 | 上限 |
|---|---|---|
| 0 结论 | 推荐哪条 + 一句话理由 + 与现状的差 | ≤5 行 |
| 1 目标函数与必要条件 | 一句目标 + ≤6 条必要条件 | ≤8 行 |
| 2 三栏表 | 事实 / 假设 / 推断 | ≤10 行 |
| 3 被推翻的假设 | 假设 → 事实 → 受影响范围 | ≤3 行 |
| 4 最小充分系统 | 必要条件 → 机制 → 归属 | ≤6 行 |
| 5 候选对比 | 改什么 / 删什么 / 代价 / 可逆性 | ≤6 行 |
| 6 评分与翻转条件 | 四维分数 + 翻转条件 | ≤6 行 |
| 7 推荐路线 | 保留 / 删除或推迟 / 顺序 | ≤8 行 |
| 8 最小验证 | 验证什么 / 怎么做 / 预登记判据 / 时间盒 | ≤3 行 |
| 9 决策点 | ≤3 个互斥选项 + 一句推荐 | ≤4 行 |
| 10 未决风险 | 缺失证据 / 会改变结论的事实 / 回退方式 | ≤3 条 |

长度控制：不复述被评估方案全文（引用 ≤5 行），不解释通用原理（原理在 `references/method.md`），不贴大段代码；细分方向超过 5 条时只保留影响主结论的，其余合并成一行「同类改法见候选表」。

## 停止规则与反合理化

停止规则：

- 目标函数与必要条件定不下来 → 停，只问一个最关键的问题。
- 没有任何候选比现状少模块、少依赖、少排期 → 写「现状方案是当前证据下的较优解」，不硬凑优化。
- 关键判断只有索引级证据 → 停在第 7 步，交验证方案，不宣布结论。
- 用户要的是细节闭合或接口设计 → 路由 `grilling` / `codebase-design`，不在本技能展开。
- 时间盒到 → 交三栏表 + 候选表 + 下一步，不写半成品推荐。

反合理化：

| 借口 | 驳回 |
|---|---|
| 方案文档写得很全，说明想清楚了 | 完整不等于必要；逐条跑必要条件与换脚本测试。文档齐全、代码为零是设计稿，不是证据 |
| 功能以后会用到，先建着 | 那是给第二个实例预付的税；没有第二个真实实例就是预付成本，推迟到实例出现 |
| 用户已经定了方案，照做就行 | 本技能的主入口就是「已定方案」；复述方案不叫评估 |
| 大方向没问题，细节不用看 | 大方向对、抽象层级错，会让每个细节都错；内核与插件的归属必须在第 4 步定 |
| 第一性原理 = 从零重想 | 不是清零，是把结论挂到目标与事实；现成设计与现成产品都是候选 |
| 没有数据，只能凭经验 | 降置信度，不拒绝结论；缺 A/B 证据就标低置信并给最小验证 |
| 直觉上明显是 X | 直觉只能生成候选；选优必须给分值或翻转条件 |
| 外部方案没测过，不能写 | 写成索引级候选 + 「需 N 小时实测」，不写成结论 |
| 成本估不准，没法比较 | 不需要精确人周；比较「净增/净减模块数 + 是否新增依赖 + 是否新增平台」即可 |
| 用户坚持要某个东西，必须保留 | 美观、习惯、成就感都是正当需求，但按目标函数重排优先级，并与可靠性线分开排期、各给时间盒 |
| 新事实推翻结论很麻烦，悄悄改掉 | 显式修正：写清哪条判断被推翻、依据什么、修正后结论；静默改写会污染后续文档 |
| 已有十来个更优解，全部写出 | 只保留影响主结论的 3–6 条；其余合并成一行，读者要的是一页可决策 |

## 边界

- 不写代码、不改文档、不跑基准；需要动手由相邻技能执行。
- 不做评分体系与全量体检（`brooks-*`）、不做 PR 双轴评审（`code-review`）、不做单函数规范（`function-spec`）。
- 不承诺无法验证的收益；不把索引级证据写成结论；不为凑出「更优解」而推荐更差的方案。
- 零第三方依赖：本技能只有 Markdown，事实采集用只读命令（如 `rg`、`git log`、日志统计）。
