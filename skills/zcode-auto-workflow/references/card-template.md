# 派卡卡文模板

把 `<>` 换成项目实际值。卡文分五段：定位、现状、测试、文档、纪律；末尾必须带质量审查尾部与停手约束，否则一张卡可能改到一半就合并或跳过审查。

## 发卡前三项必查

| 项 | 卡文里必须出现 | 判据 |
|---|---|---|
| worktree 定位 | 起始 commit、分支名、worktree 绝对路径 | 三项同时出现 |
| 停手约束 | 「不要合并 main、不要删分支」+ 交付四项证据 | 明确禁止合并与删分支 |
| 质量审查尾部 | 四条要求，第 3 条按「发现 N / 整改 M / 保留 K」记账并附理由 | 四行齐全 |

缺一项就不要发。

## 模板

```markdown
# 卡 <编号>：<一句话目标>

## 开工定位
- 仓库 `<仓库路径>`，从 `main = <commit>` 起开独立 worktree：分支 `zcode/<slug>`，路径 `<worktree 路径>`。
- 只在这个 worktree 里改。不要动主工作区与别人的 worktree，也不要动用户保留的分支。
- 开工前读：`docs/10-工程宪法.md`、`docs/11-代码规约.md`、与本次改动相关的规格文档；项目根 `AGENTS.md`。
- 做到「分支自测通过 + `<门禁命令>` 全绿」就停手：不要合并 main、不要删分支。把分支名、提交清单、门禁输出与自测账目报给用户。

## 要达成的现状（交付后应为真）
1. <可验收的行为 1，带文件路径或端点>
2. <可验收的行为 2>
3. <边界：不做什么，避免扩范围>

## 测试（必须覆盖）
- <正常路径>
- <错误/边界路径>
- <并发或恢复路径>
- 若个别用例失败且其它全绿，先判断是不是并行跑门禁的已知误报，等两分钟复跑；不要改代码掩盖。

## 文档（只写此刻为真）
- <要改的文档与节>
- `<TASKS.md>` 若有对应待办就删，其它不动。
- 有欠账就记 `DEBT.md`（编号递增）；没欠账不硬凑。

## 交付纪律
- 提交按 diff 增删计 ≤400 行；交付物只写现状、不写改动史。
- 收尾必须跑门禁全绿，并跑交付物检查，在回复正文报一行：`交付物检查：PASS（N 个文件）`。

## 质量审查要求（每次任务执行都必须做）
1. 提交前过 function-spec（函数级规范审查）；有对外行为改动的再过 code-review 双轴。
2. 再过 brooks-review（代码质量审查），不得留 Critical。
3. 按「发现 N / 整改 M / 保留 K」记账写进收尾提交说明；保留项逐条附理由。
4. 同一个坑第二次踩到时，先写测试再改代码。
```

## 使用要点

- 卡文里写「交付后应为真」，不写「之前怎样、这次改成怎样」。
- 一卡一 worktree；卡文必须写明分支名与 worktree 路径，否则两张卡会挤同一目录。
- 末尾那两段（质量审查、停手约束）不能省：省了会出现「改完顺手合并」和「跳过审查」。
- 卡文先落盘成文件再粘贴，便于复核、重派与事后追溯。
