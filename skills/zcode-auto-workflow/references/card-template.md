# 派卡卡文模板

卡文是给执行者的工序书：**七段齐全 + 九项必查全过**才可派。缺段或缺判据的卡派下去，执行者会自己补剧情——补出来的是他的假设，不是你的验收。

## 发卡前必查（九项，缺一不派）

| # | 项 | 机械判据 |
|---|---|---|
| 1 | 开工定位 | 起始 commit 等于当前 `main` 头（`git rev-parse --short main` 核过）、分支名、worktree 绝对路径，三者同时出现 |
| 2 | 停手约束 | 明确写「不要合并 main、不要删分支、不要 push」+ 要求交付四项证据（分支、提交、门禁输出、自测账目） |
| 3 | 现状可验收 | 每条现状 = 触发条件 + 可观测结果 + 反面（不该发生什么）；「重构得更清晰」「补上健壮性」这类无观测项不合格 |
| 4 | 现状→测试映射 | 每条现状至少一条测试，测试条数 ≥ 现状条数，且注明覆盖哪条现状 |
| 5 | 竞争与错误语义 | 涉及并发、状态机、外部调用、异步的卡必须写：谁赢、输家做什么、被拒时接口返回什么、写哪些事件 |
| 6 | 文档引用点 | 列出具体文件与节；涉及已有欠账写「`DEBT.md` 删除哪一条」；涉及 ADR、契约、状态机表必须点名 |
| 7 | 边界 | 至少两条「不做」，防止范围蔓延（重构、拆分、依赖升级一律另卡） |
| 8 | 预算与审查 | 产品代码 diff ≤400 行；质量审查四小节齐全 |
| 9 | 首行与唯一码 | 第一行只有 `卡<N>-<码>`：码 2 位、取自 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（去 0/O/1/I），整行 ≤7 字符；名称从第二行开始；码同时写进回执文件名与回执首行 |

## 卡文七段（按序，缺段不算卡文）

1. 开工定位（含停手）
2. 要达成的现状
3. 不做与边界
4. 测试（现状→测试映射）
5. 文档与账目
6. 交付纪律
7. 质量审查尾部

## 模板

```markdown
卡<N>-<码>
# <一句话目标>

## 开工定位
- 仓库 `<仓库路径>`，从 `main = <commit>` 起开独立 worktree：分支 `feat/card<N>-<slug>`，路径 `<worktree 路径>`。
- 只在这个 worktree 里改。不要动主工作区与别人的 worktree，也不要动用户保留的分支。
- 开工前读：项目根 `AGENTS.md`、<必读规范>、<相关规格文档>、<本次要改的模块>。
- 做到「分支自测通过 + `python scripts/gate.py` 全绿」就停手：不要合并 main、不要删分支、不要 push；把分支名、提交清单、门禁输出与自测账目报给用户。

## 要达成的现状（交付后应为真）
1. <触发条件> → <可观测结果>；反面：<不该发生什么>。
2. <同上>
3. <对外口径：字段、返回码、事件名。没有就写「无对外口径变化」>

## 不做与边界
- 不做 <重构 / 拆分 / 依赖升级>，需要就另开卡。
- 不改 <明确不动的文件或行为>。
- 不引入 <全局锁 / 新线程 / 新依赖>，除非现状条目明确要求。

## 测试（必须覆盖，逐条映射到现状）
| 现状 | 测试 | 断言什么 |
|---|---|---|
| 1 | `tests/<路径>::<用例>` | 正例：<...> |
| 1 | `tests/<路径>::<用例>` | 反例：<...> |

- 并发/时序类：判据必须能在修复前红、修复后绿；只描述外部可观测结果（最终状态、事件条数、返回码、是否阻塞），不描述实现内部窗口。
- 若个别用例失败且其它全绿，先判断是不是并行跑门禁的已知误报，等两分钟复跑；不要改代码掩盖。

## 文档与账目
- `<docs/xx-...md>` 的 `<节>`：写什么（只写现状）。
- `DEBT.md`：删除 `<编号>`（已偿还）；`TASKS.md`：删除对应待办。没有这两项就各写一行「无」。
- 涉及 ADR / 契约 / 状态机表：点名 `<docs/adr/....md>`、`contracts/`、`tests/state_tables.py`。

## 交付纪律
- 提交按 diff 增删计 ≤400 行（产品代码）；交付物只写现状、不写改动史。
- 收尾必须跑 `python scripts/gate.py` 全绿，并跑 `python scripts/check_artifacts.py .`，在回复正文报一行：`交付物检查：PASS（N 个文件）`。
- 收尾把最终回执写进 `<回执目录>\HANDOFF-card<N>-<码>.md`（回执目录见 profile，仓库外）。字段固定：
  1. 首行 `卡<N>-<码>`；
  2. 分支与提交清单（短哈希 + 标题）；
  3. 七条门禁逐条结果，末条原样抄 `交付物检查：PASS（N 个文件）`；
  4. 行数账目（产品 / 测试 / 文档）；
  5. 用例账目（新增或改动的测试文件与条数，逐条映射到现状）；
  6. 自检账目（发现 / 整改 / 回退 / 保留，保留项逐条理由）；
  7. 需 Lead 定夺项（没有就写「无」）。
- 回执写完，在 ZCode 回复正文最后一行写：`回执：<路径>`。

## 质量审查要求（每次任务执行都必须做）
1. **函数级**：新增或修改的每个函数逐个核对——命名说清意图、参数不超过四个、单一职责、错误契约明确（返回空值还是抛异常要写清）、docstring 与类型提示齐全、嵌套不超过三层。
2. **代码质量**：查重复代码、过长函数、过深嵌套、命名含糊、注释与代码不符、死代码六类；不得留严重项。
3. 按「发现 N / 整改 M / 保留 K」记账写进收尾提交说明；保留项逐条附理由。
4. 同一个坑第二次踩到时，先写测试再改代码。
5. **审查只能由你本人完成**：不得开子智能体、不得另起代理或外部会话代审、不得转交；账目只写你本人逐条读本次 diff 与代码得出的结论，转述别人的判断不算审查。
```

## 设计类卡的额外槽位

并发、状态机、线程、事务、异步这几类卡，写卡时逐条回答下表，答案落进「要达成的现状」或「不做与边界」：

| 问 | 落点 |
|---|---|
| 谁在什么状态下允许做什么 | 前置状态与迁移判定 |
| 两个写者撞上时谁赢、输家做什么 | 仲裁规则（先写后写、条件更新、退让、事务内重读） |
| 被拒时接口返回什么、写什么事件 | 对外语义（状态码、事件名、载荷） |
| 哪个线程用哪条连接、跨线程共享什么 | 连接与可见性归属 |
| 停机、异常、超时怎么走 | 非正常路径也要有判据 |
| 哪些承诺不能变 | 兼容与回滚（签名、旧数据、旧事件） |

## 验收判据三条铁律

1. **能红→绿**：修复前必须失败、修复后通过。写不出反例的判据不算验收。
2. **只描述外部可观测结果**：最终状态、事件条数、返回码、是否阻塞、是否超时。不写「插在读与写之间」这类实现内部窗口——修好之后那个窗口不存在，测试无从复现。
3. **并发类正反成对**：正例证目标行为，反例证没有放宽原有约束（例如「非叫停的竞争仍抛错」）。

## 交接场景（卡文由别的会话或模型写）

派卡人不等于写卡人时，主控先跑必查八项，任一不过就打回重写，不「先派了再说」。另加四项核对：

| 核对 | 方法 |
|---|---|
| 起始 commit 是当前 `main` 头 | `git rev-parse --short main` |
| 卡文里的文件路径真实存在 | `Test-Path` / `git ls-files <路径>` |
| 欠账编号与 docs 节真实存在 | `Select-String` 命中 |
| 测试文件名真实存在或明确标「新增」 | `git ls-files tests/` |

## 使用要点

- 首行只放 `卡<N>-<码>`：执行者把第一行当会话标题，窗口标题栏只显示这一行；码短、去易混字符，截图识别与多窗对账都靠它，名称写在第二行。
- 回执必须落盘而不是只口头报：执行者窗口里的输出主控读不到，回执文件是可机械核对的唯一通道。
- 卡文送达：收件人在电脑旁时整段贴进对话窗口（Markdown 代码块，可直接复制），文件路径只作追溯；无人值守或接续换会话时才只给路径与回执路径。
- 卡文只写「交付后应为真」；改动史留给提交说明与账本。
- 一卡一 worktree；分支名与路径写死，否则两张卡挤同一目录。
- 末尾两段（停手、质量审查）不能省：省了会出现「改完顺手合并」与「跳过审查」。
- 卡文先落盘成文件再粘贴，便于复核、重派与事后追溯。
- 长度以「执行者不用追问就能开工」为准；超过 400 行预算的设计就拆卡，不压成巨卡。
