# zcode-auto-workflow 最小评测

## 评什么

证明技能能按 ZCode 的真实界面与任务状态库把一张卡从「写好」推到「合并且有证据」，以及在无人看管条件下守住并发上限、巡检、额度检查与收尾时刻。判据看动作顺序与证据，不看最终代码质量。

## 怎么跑

1. 新会话加载 `zcode-auto-workflow`（`skill` 工具按 name 加载，或用户 `/zcode-auto-workflow`）。
2. 把下面某个 case 全文作为用户消息，末尾只加一句：「按 zcode-auto-workflow 执行，先给计划再动手。」
3. 收集完整输出，按机械判据逐条判定；证据存到 `evidence/YYYY-MM-DD-<model>/`（不入库，或只入库摘要）。
4. 换模型或改技能后重跑同一批 case，比较命中率。

## case 1：单卡派发

```text
卡文已写在 D:\proj\cards\007.md，分支 zcode/fix-login，worktree D:\proj-wt\fix-login。
仓库 D:\proj，main 干净。派给 ZCode 并盯到完成，完成后复核、跑门禁、合并、清理，给我回执。
```

## case 2：无人看管夜班

```text
我睡了，替我推进 D:\proj：每批最多两张卡，早上 8 点收尾，10 点看一次额度。
卡文模板和交接账本都在仓库里。别吵我，出问题留证据。
```

## 机械判据（18 条，全过才算 PASS）

| # | 判据 | 判定方法 |
|---|---|---|
| 1 | 第 0 步检查 ZCode 窗口、`tasks-index.sqlite`、git main、门禁、定时五項，缺项写明降级 | 输出前 20 行内能数出五项；缺项有「降级/未做」 |
| 2 | 派卡顺序为「新建 → 选项目 → 完全访问 → 粘贴 → 发送」，且点明「选项目会清空输入框」 | 顺序错或漏「先选项目」→ 不通过 |
| 3 | 盯卡同时用任务状态库与至少两条证据（worktree 提交、未提交改动、会话文件 mtime） | 只报状态、不看进展 → 不通过 |
| 4 | 完成报告含状态、分支与提交数、门禁结论、交付物检查四项 | 缺任一 → 不通过 |
| 5 | 夜班声明并发上限按 profile（现为 3，含子智能体）与当日额度到期时刻，并声明窗口外停派 | 上限与当日不一致、或没提窗口外停派 → PARTIAL |
| 6 | 额度检查对齐当日额度窗口（到期前触发），结论三选一（领额度继续 / 继续 / 收工并删定时） | 自造固定时刻或缺结论 → 不通过 |
| 7 | 合并前串行门禁、冲突按语义取并集；不出现「并行跑门禁」 | 出现并行门禁或先合后验 → FAIL |
| 8 | 播报同时含「已完成 / 在跑 / 下一步」；界面坐标声明「以当场截图为准」 | 缺项或凭记忆连点 → PARTIAL |
| 9 | 分清两条「新建」：派卡说 ZCode「新建任务」，接续说 DSH「新会话」，并给出各自判据 | 用 ZCode 新建任务做接续、或用 DSH 新会话派卡 → FAIL |
| 10 | 卡文按七段写，且过十项必查（定位/停手/现状可验收/现状→测试映射/竞争与错误语义/文档引用点/边界/预算与审查/首行与唯一码/用例不打掉宿主） | 缺段、无测试映射、或起始 commit 不等于当前 main 头 → FAIL |
| 11 | 门禁按证据跑：分支上必跑一次；合并后仅当 `git diff --stat <分支头> <merge>` 非空才跑，并在回执写明跳没跳与理由 | 无条件连跑两次、或树不同却不跑 → PARTIAL |
| 12 | 卡文第一行只有 `卡<N>-<码>`（≤7 字符，码 2 位、去 0/O/1/I），名称从第二行开始 | 首行写了名称或描述、或超过 7 字符 → FAIL |
| 13 | 收尾回执落盘在 `<回执目录>\HANDOFF-card<N>-<码>.md`，字段齐全（提交、七条门禁、PASS 文件数、行数、用例、自检、定夺项） | 只口头报回执、字段缺项、按未完成处理 |
| 14 | 收件人在电脑旁（用户在场要卡文）时，卡文整段以 Markdown 代码块贴在对话窗口、可直接复制；落盘路径只作追溯 | 只给路径让用户自己打开文件、或只给摘要 → FAIL |
| 15 | 卡文「质量审查要求」写明审查只能由执行者本人完成（禁子智能体、禁代理或外部会话代审），审查账目是本人结论 | 卡文缺该句、或输出里出现用子智能体做审查、转述他人结论当审查账目 → FAIL |
| 16 | 复核证据来自主控本人：亲自逐分支看 diff，并在分支上串行跑一次全量门禁；不采信执行者自述 | 直接按「执行者说全绿」合并 → FAIL |
| 17 | 回执第 7 项「需 Lead 定夺项」在合并前逐条答复，答复写进账本 | 未答复即合并、或只口头带过 → FAIL |
| 18 | 门禁红时先判「用例把宿主打掉」：`os.kill(pid, 0)` 存活探测、测试进程内 `taskkill /T /F`、`KeyboardInterrupt` 停在 `join`/`communicate`，再判真缺陷 | 把这类红当产品缺陷改代码，或加重试/跳过 → FAIL |

## 不合格特征（出现任一即 FAIL）

- 没看到卡文就派卡，或派卡后才发现项目选错。
- 卡文首行写了名称或长标题（窗口标题被截断，图像识别对不上卡）。
- 收尾只口头报回执，没有落盘文件。
- 人在电脑旁却只给卡文路径，让用户自己去文件里翻找复制。
- 把审查交给子智能体或另起的代理/会话，拿别人的结论充当审查账目。
- 执行者说门禁全绿就直接合并，主控没有亲自复跑。
- 回执里的定夺项没有答复就合并。
- 用例用 `os.kill(pid, 0)` 探测存活或在测试进程里 `taskkill /T /F`，把 pytest 进程或宿主一起打掉。
- 模式用默认「自主模式」，任务卡在等审批。
- 并行跑多个门禁并接受其误报。
- 未到终态就合并，或合并后不复跑门禁。
- 无人看管时超过并发上限继续派卡。
- 宣称完成但拿不出分支、提交、门禁、交付物四项证据。
